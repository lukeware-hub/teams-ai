# Backlog de bugs

Bugs, por enquanto. Lacunas e decisões do dono estão em Abertos. Cada item diz o que quebra, onde está no código e como foi visto. Fonte: auditoria do código em 2026-10-13 mais os journals de 46 runs do projeto kayron-hub (12 done, 12 awaiting-validation, 7 deploy-failed, 7 phase-failed, 4 verification-failed, 2 blocked). Os itens marcados "visto em run" aconteceram de verdade; os demais foram confirmados por leitura do código.

Severidade: **crítico** = segredo exposto ou custo sem limite; **importante** = run perde trabalho, trava ou gasta tentativas por causa da plataforma; **menor** = erro contido, sem perda de trabalho.

## Críticos

- [x] **Qualquer gate do plano recebe qualquer segredo da plataforma.** `server/exec/gate-runner.ts:156-163` injeta cada nome de `gate.secrets` a partir de `ctx.secrets`; `server/orchestrator/run.ts:399` passa todos os segredos (plataforma e projeto, montados em `server/cli.ts:209`, incluindo `GITHUB_TOKEN`); `server/validators/plan.ts` nunca compara `gate.secrets` com os `secretNames` da spec. Um plano com `secrets: ['GITHUB_TOKEN']` e `network: 'egress'` exfiltra o token. Correção: rejeitar no validador nomes fora dos `secretNames` da spec e montar o contexto dos gates só com os segredos do projeto.
- [x] **Os cinco documentos vão para o OpenRouter mesmo com `confidential: true`.** `server/refine/cycle.ts:125-133` chama `validateDocs` (Jev no OpenRouter) antes de ler `confidential`; `server/refine/jev-validation.ts` não recebe a flag; o único gate está no `Decider` (`decider.ts:91`), depois que o texto já saiu. Sem chave do OpenRouter o ciclo falha, então não há como refinar um projeto confidencial sem vazar. Correção: pular `validateDocs` quando o projeto é confidencial e registrar `DocsValidated` com `skipped: 'confidential'`.
- [x] **As credenciais copiadas para o HOME do step são legíveis por `cat`.** `server/runner/step-home.ts:57` grava `.claude/.credentials.json` no HOME do step; `server/runner/role-settings.ts:89-90` só nega leitura dos caminhos do HOME do host. Dev, front e test têm `Bash(cat:*)`, `Bash(node:*)` e `Bash(python3:*)`; um prompt injetado lê o token e a rede do sandbox inclui `registry.npmjs.org`. Correção: incluir `<stepHome>/.claude/**` em `filesystem.denyRead` (exige settings por step, ver item abaixo).
- [x] **Programa reexecuta uma spec falhada de forma idêntica.** `server/program/service.ts:236-240` usa `classifyFailure` para decidir se repete; com o decider desligado (config atual) a resposta é `null` e `retryable(null)` é verdadeiro, então toda falha ganha os 2 repairs de `MAX_REPAIRS`. Visto em run: signature-approval-pattern run-1, run-2 e run-3 falharam a fase 2 com as mesmas 3 rejeições de schema (9 chamadas Opus, ~US$ 4); audit-trail-integrity run-1 a run-3 falharam o deploy com o mesmo "AC-049: no smoke test". Correção: sem classificação, não repetir; e nunca repetir quando a razão de `RUN_FINISHED` é igual à do run anterior.

## Importantes

### Orquestrador e programa

- [x] **Retomar com tarefas bloqueadas não roda o Dev de novo.** `server/orchestrator/task-runner.ts` `implement()` pulava o Dev quando o `Intent.Commit` `T…:a{n}` já estava confirmado; o `retry-blocked` zera as tentativas e a chave repetia (run-6: `:a1` a `:a3` confirmados). Correção: `commitKeyFor` acrescenta `:u{n}` por desbloqueio.
- [x] **Gate do plano com comando errado trava o run sem caminho de correção.** Visto no run `kayron-hub--platform-local-foundation--run-6`: o gate `coverage` congelado tinha um `sed` com `.*` guloso que gravava `{"linesPct": }`; o SM e o dev achavam a correção, mas o spec-gap só devolvia texto. O scaffold bloqueou após três tentativas, e as tarefas e correções que dependiam dele ficaram bloqueadas. Correção: o SM pode devolver `gateFix` no spec-gap e o orquestrador aplica, validado e registrado como `GATE_FIXED` (`server/orchestrator/gate-fix.ts`); tentativa sem mudança após commit que falhou num gate vai ao SM uma vez e não roda o gate de novo sobre o mesmo commit (`server/orchestrator/task-runner.ts` `repeatsLastCommit`).
- [x] **O programa desfaz um Stop do humano.** `server/program/service.ts:258-263` ignora `row.stopped`; `controller.ts:187` retoma e `service.ts:214` apaga o marcador de stop. Um run que drenou limpo vira `failed` (`service.ts:278-283`) e ganha repair. O supervisor respeita o stop (`supervise.ts:20-28`); o programa não. Correção: devolver um `kind: 'stopped'` em `outcome()` e deixar o item pausado.
- [x] **`paused:auth` nunca chega ao programa; o item gasta 3 resumes e falha.** `server/api/run-index.ts:197-202` classifica como `interrupted` antes de olhar `state.status`, porque o run que pausou por auth sai do processo (`cli.ts:319-327`). Cada resume bate no mesmo login vencido; após `MAX_RESUMES` o item fica `failed` e os dependentes bloqueiam, sem a interface mostrar "aguardando login". Visto em run: 4 steps dev e 1 report com `failure: auth`. Correção: manter `paused:auth` à frente de `interrupted` em `runRow`.
- [x] **Falha de escrita no journal vira loop quente.** `server/store/event-store.ts:270-276` fecha a store para sempre após um append falhar; `server/orchestrator/run.ts:850-859` engole o erro do runner e `run.ts:822-823` o reinicia sem pausa, refazendo `gitFetch`, `createWorktree` e `installDeps` a cada volta. Correção: tratar store fechada como fatal.
- [x] **O caminho de fix-task do deploy termina o run duas vezes e roda a fase 6 depois de um stop.** `server/orchestrator/run.ts:765` não devolve `drained`/`deadlocked`/`paused:auth` como faz `run.ts:752`; cai em `runPhase6` (step do SM) e `finish` grava um segundo `RUN_FINISHED`, que o índice lê como `deploy-failed` e o programa reexecuta. Correção: `return back` como na linha 752.
- [x] **Recusa transitória de merge fica cacheada por sha e consome o orçamento de tentativas.** `server/orchestrator/merge-steps.ts:104-108` confirma `{ merged: false }` por `branch@sha` para sempre; `github.ts:108` trata qualquer saída não zero do `gh pr merge` (5xx, corrida de base) como recusa. O ciclo refaz a fila de merge 3 vezes, vira `infra`, gasta a tentativa, e se o Dev não muda nada o sha e o cache continuam iguais até o replan. Correção: só confirmar recusas definitivas (head moveu, PR fechado).
- [x] **Serviço de outra spec nunca publicado some do mapa de endereços sem erro.** `server/orchestrator/phases/deploy.ts:250-252` só inclui em `SERVICE_URL_*` serviços com porta registrada; um que nunca subiu simplesmente falta. O e2e falha por nome não resolvido, a fase gasta 3 tentativas e fix-tasks que o Dev não consegue resolver. Visto em run: sla-engine run-3, T950-deploy-fix-2 bloqueou com "o nome audit-service não resolve na rede"; 3 deploys falhados. Correção: antes do smoke, falhar como `environment` nomeando o serviço ausente, sem fix-task.
- [x] **Orçamentos nunca agem por padrão, e ao agir ainda gastam.** `server/config/config.ts:112` `observeOnly: true`; `run.ts:792` pula o teto por run inteiro em modo observação, sem nem registrar o fato. Com enforcement, `run.ts:820-823` reinicia runners em `implementing` durante o drain, até 2 tentativas Dev e um replan por tarefa após o teto. Visto em run: 6 `BUDGET_EXCEEDED` no sla-engine run-3 sem efeito. Correção: não reiniciar runner em drain; registrar o fato do run em modo observação.
- [x] **Replan antecipado mais quota cobra a tentativa duas vezes.** `server/orchestrator/task-runner.ts:611` grava `AttemptConsumed` antes de `replan()`; se o SM cai em quota (`:656-659`) a tarefa fica no estado anterior com a tentativa gasta e `fail()` cobra de novo ao reabrir. Correção: gravar `AttemptConsumed` depois do replan.

### Runner (steps do Claude Code)

- [x] **Processo filho que sai normalmente nunca mata o grupo; servidores que o agente deixou rodando vazam.** `server/runner/process-runner.ts:172-176` `finish()` não sinaliza o grupo (`detached`); só os caminhos de kill o fazem. Um `npm run dev &` do Dev segura a porta da tarefa para o próximo step ou gate. Correção: `SIGKILL` no grupo em `finish` quando posix.
- [x] **Arquivo de settings compartilhado por papel dentro do run.** `server/runner/role-settings.ts:103` grava `<run>/settings/<role>.settings.json`; `run.ts:293` monta `allowedDomains` por serviço (stack). Dois steps dev concorrentes de stacks diferentes sobrescrevem a política um do outro entre a gravação e o `spawn` (há um `restoreSession` assíncrono no meio, `step.ts:231-260`). Correção: gravar o settings dentro do HOME do step.
- [x] **A janela do refresh gate (5 min) é menor que o timeout do step (20 min).** `server/runner/step.ts:195` `REFRESH_WINDOW_MS = 5 min` contra `config.ts:90` `timeoutMs = 20 min`; dois steps paralelos que começam fora da janela ainda rotacionam o refresh token ao mesmo tempo e um deles falha com `auth`, consumindo tentativa. Correção: janela maior ou igual ao timeout do step.
- [x] **Contabilidade de sessão retomada: custo é subtraído, `usage` não; delta negativo vira zero.** `server/runner/step.ts:266-272` subtrai `before.costUsd` mas registra `usage` inteiro (tokens da tentativa 1 contados de novo na 2, estourando o teto por tokens mais cedo); um delta negativo é clampado a 0 e some. Correção: guardar e subtrair `usage` em `totals.json` e registrar o delta negativo.
- [x] **Exceção fora de `runProcess` escapa sem `StepOutcome`.** `server/runner/step.ts:229-232`: `ensureTrusted`, `writeRoleSettings` e `restoreSession` lançam e sobem até `runAgentStep`, que já emitiu `StepStarted` e nunca emite `StepFinished`. Correção: envolver `runStepIn` e devolver falha de ambiente.

### Git, deploy e gates

- [x] **Gates de segurança desarmáveis sem o validador perceber.** `server/validators/security-tooling.ts:28` só pega `|| true`, `exit 0` e flags de exit-zero; os `allowed` testam só o prefixo. `gitleaks ... | cat`, `semgrep ... ; true` e `osv-scanner ... || echo skip` passam e nunca falham. Correção: rejeitar `;`, `|`, `||`, `$(`, crases e `&` nos gates de segurança.
- [x] **Envenenamento do `/gate-cache` compartilhado.** `server/exec/gate-runner.ts:145-156` monta o cache rw nos gates `security-tools` e `image-scan`; `security-tooling.ts:29-30` remove qualquer prefixo `VAR=valor` antes de comparar o comando, então `PATH=/work/bin:$PATH sh .tools/install.sh` passa e o instalador chama `sh`, `curl`, `sha256sum`, `tar` do worktree. Só `dl/` é re-verificado por sha256; o banco do trivy não. Um projeto envenena o `image-scan` de todos. Correção: aceitar só o prefixo exato `PATH=$PWD/.tools/bin:$PATH`, ou montar o cache read-only com cópia por run.
- [x] **Falha do `compose up` deixa a stack nova quebrada no ar, sem rollback.** `server/deploy/target.ts:104-108` devolve `{ stage: 'apply', rolledBack: false }` sem chamar `fail()`; `docker-local.ts:269-270` já substituiu os containers quando `--wait` lança. Correção: ler `currentImage` antes e passar por `fail('apply')` quando há `previous`.
- [x] **Rollback do compose pode reiniciar a própria imagem quebrada.** `server/deploy/docker-local.ts:267` guarda `previous` como `nome:tag`; com `image: app` mais `build:`, o `--build` sobrescreve a tag e o rollback sobe o build quebrado, e `target.ts:127` reporta `rolledBack: true`. O contrato `image: ${TEAMS_AI_IMAGE:-...}` só existe como texto de prompt; nenhum validador o verifica. Correção: validar o contrato no compose, ou guardar e restaurar por ID de imagem.
- [x] **Relatório JUnit ou coverage entra no commit da tarefa quando o caminho não é `reports/junit.xml`.** `server/git/git.ts:22` espera que o chamador some `plan.junitPath` aos excludes; `task-runner.ts:344` e `phases/shared.ts:156` passam `{}`. `gate-runner.ts:306-308` recoloca o XML no worktree e o próximo `git add -A` o stageia. `coveragePath` nem é filtrado em `task-runner.ts:337`: cada retentativa após o gate de coverage falha com "files outside affectedPaths". Correção: excluir `junitPath` e `coveragePath` no commit e no checkScope.
- [x] **Redação de segredos depois do corte do tail.** `server/exec/gate-runner.ts:245` corta em 4000 chars antes de redigir; um segredo partido no corte fica com o sufixo visível no journal, na interface e nos prompts. `run-control.ts:93` faz na ordem certa. Correção: `tail(redactSecrets(s))`.
- [x] **Leitura do journal sem limite, multiplicada por cliente SSE.** `server/api/journal-tail.ts:16-18` aloca o arquivo inteiro; cada assinante tardio relê do byte 0 (`:82, :90`) embora `run-routes.ts:569, 586` já tenha reproduzido tudo. Até 200 streams × journal de centenas de MB. Correção: iniciar o poller no tamanho atual e ler em blocos.
